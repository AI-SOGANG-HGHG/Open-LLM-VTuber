## 지금 접속하기

주소: <http://localhost:12393/>. 이번 확인에서는 기존 서버가 이미 실행 중이어서 유지했고 기본 브라우저로 주소를 열었다. 서버를 새로 시작했다는 의미는 아니다.

서버가 꺼져 있으면 저장소 루트에서 다음 명령으로 실행한다.

```powershell
powershell -ExecutionPolicy Bypass -File .\start-local.ps1
```

이 명령으로 실행한 서버는 해당 터미널에서 `Ctrl+C`로 종료한다. `stop-local.ps1`은 기록된 백그라운드 프로세스만 종료하는 용도다.

## 현재 기능과 확인 수준

| 기능 | 구현·현재 설정 | 확인 수준 |
| --- | --- | --- |

| 한국어 음성 출력 | Edge TTS `ko-KR-SunHiNeural` | 오늘 WAV 데이터 수신 확인. 스피커 청취는 직접 확인 필요 |

| 캐릭터 설정 전환 | `characters/*.yaml` 프리셋, persona/model/voice 설정 | 전환 처리 존재. 프리셋별 말투·모델·음성 및 복귀는 직접 확인 필요 |
| 응답 중단 | WebSocket interrupt 처리 | 실제 재생·마이크·다음 대화와 함께 검증 필요 |

캐릭터 설정을 바꿀 수 있다는 것과 성격에 따라 행동이 일관되게 달라진다는 것은 별도 검증 항목이다. 기존 프리셋에는 영어·중국어 역할 설정도 있으므로 현재 기본 설정의 한국어 말투와 다를 수 있다. 브라우저 웹 버전 검증 결과를 별도 데스크톱 펫 앱이나 방송 연동의 완료로 보지 않는다.

## 먼저 10–15분 동안 확인할 것

개인 정보 대신 아래 시험 문장을 사용한다. 한 탭에서 순서대로 진행한다. 메뉴 이름은 UI 언어에 따라 다를 수 있다.

| 순서 | 조작·입력 | 합격 기준 | 실패 시 먼저 볼 것 |
| --- | --- | --- | --- |
| 1. 화면 | 페이지를 열고 캐릭터가 나타나는지 확인 | 캐릭터와 채팅 UI가 정상 표시되고 연결 오류가 없음 | 브라우저 F12 → Console/Network. JS·모델·텍스처의 실패 요청 |
| 2. 텍스트·음성 | 새 대화를 만든 뒤 “한국어로 한 문장만 자기소개해 줘” | 한국어 답이 표시되고 실제 소리가 들림. 캐릭터 입이 발화에 맞게 움직임 | 화면 답 유무, 브라우저 음소거·자동 재생, 출력 장치, 서버 TTS 오류를 구분 |
| 3. 단기 기억 | “이번 시험의 좋아하는 색은 보라색이야” → 다른 질문 한 번 → “내가 좋아하는 색은?” | 같은 대화에서 보라색을 답함 | 현재 대화 선택, Agent 입력 문맥. 장기 기억 성공으로 판정하지 않음 |
| 4. 기록 복원 | 다른 대화를 만들었다가 이전 기록을 다시 선택하고 색을 질문 | 이전 기록이 화면에 복원되고 그 대화의 정보를 답함 | `chat_history/` 저장 파일 존재와 기록 불러오기 메시지. 파일 본문은 공유하지 않음 |
| 5. 새 대화 | 새 대화에서 “이번 대화에서 내가 좋아하는 색을 말했어?” | 새 대화에 이전 시험 정보가 자동으로 섞이지 않음 | 알려진 Agent 상태 공유 문제를 포함해 조사. 우연히 색을 맞혔다고 바로 통과시키지 않음 |
| 6. 마이크 | 권한 허용 후 “오늘 할 일을 두 가지 추천해 줘”라고 짧게 말함 | 전사가 실제 발화와 대체로 일치하고 답·음성이 이어짐 | Windows 입력 장치, 브라우저 마이크 권한·음량, ASR 전사 로그 |
| 7. 중단 | 긴 답을 요청하고 발화 도중 UI의 중단 기능을 사용 | 재생·생성이 멈추고 이후 짧은 질문이 정상 처리됨 | 재생 큐 정지와 서버 작업 취소를 각각 확인. 말로 끼어들기는 별도 항목 |
| 8. 캐릭터 | 설정/캐릭터 선택 메뉴에서 다른 프리셋 선택 → 같은 질문 → 기본 설정으로 복귀 | 선택한 캐릭터·말투가 반영되고 복귀 후에도 정상 대화 | `characters/`, persona와 모델 매핑. 일관된 성격 검증은 반복 평가가 필요 |

새로고침 뒤에도 기록이 목록에서 선택되는지 추가로 확인한다. 새로고침만으로 특정 대화가 자동 선택되는지는 별도 UI 동작이며 기록 유실과 구분한다. 화면/카메라 기능이 UI에 보이면 직접 선택한 시험 이미지로 물어보고 이미지의 구체적인 정보를 맞히는지 확인한다. 이 항목은 아직 통과 처리하지 않았다.

대화 창 두 개를 열어 다른 사람처럼 동시에 쓰는 검증은 현재 P0 과제다. 소스에서 동일 Agent 참조 공유가 확인됐으므로 여러 사용자·봇의 격리를 보장하는 상태로 안내할 수 없다. 자세한 근거는 [AIRI 포팅 검토](airi-porting-review.md)를 참고한다.

## 부족한 부분의 우선순위

1. **연결별 대화 상태 격리와 로그 마스킹.** 다중 캐릭터·사용자·봇 이전의 기반 작업이다. 설정 객체를 DEBUG 로그로 기록하는 경로가 있어 API 키·토큰이 원문으로 남지 않도록 수정해야 한다.
2. **반응 속도와 음성 사용성.** 이번 한 번의 짧은 인사는 첫 음성 데이터 수신 약 10.62초, 전체 턴 약 10.74초였다. 이는 실제 스피커 재생이나 LLM 첫 토큰 지연이 아니다. ASR·LLM 첫 토큰·TTS 첫 청크·브라우저 재생 시작을 각각 측정해야 원인을 좁힐 수 있다.
3. **캐릭터와 기억을 검증하는 방법.** 현재 persona 문자열과 전체 대화 문맥만으로 목표한 성격·선별 기억을 구현했다고 판정할 수 없다. 기억의 정정·삭제·소유 범위와 고정 질문/과제별 비교 기준이 필요하다.
4. **게임과 외부 행동.** AIRI는 참조 체크아웃만 있다. 한 봇 접속과 이동·채집·식사부터 구현하고 실제 상태 변화로 성공을 판정해야 한다. Jev·방송 연동·8개 봇·AWS 운영도 미완료다.

## 실패를 기록할 형식

각 항목은 `미실시 / 통과 / 실패 / 부분 통과` 중 하나로 남긴다. 최소 기록은 다음과 같다.

```text
날짜 / 브랜치 / HEAD와 로컬 수정 여부:
선택한 캐릭터 / 입력 방식:
재현 입력과 조작 순서:
기대 결과:
실제 결과 / 대기 시간:
브라우저 Console·Network의 관련 오류 또는 서버 오류 요약:
```

API 키와 개인 대화를 제거한 오류 요약만 공유한다. 현재 서버 로그에는 마스킹을 보완할 경로가 있으므로 원본 로그나 `conf.yaml` 전체를 붙이지 않는다.

오늘의 자동 확인 요약은 Git 제외 폴더 `tmp/current-session-check.json`, 수신 음성 샘플은 `tmp/current-session-output.wav`에 있다. 서버는 실제 Gemini와 TTS를 호출했으며 시험 클라이언트는 수신 후 재생 완료 신호만 보냈다. 실제 브라우저 재생·마이크·표정·기록·전환·중단은 위 절차로 확인해야 한다.

## 같은 날 추가한 대기 원인 조사

- 기존 서버 로그에서 23:05:04의 요청은 첫 문장 분리까지 약 16.1초 걸렸다. 해당 응답의 음성 생성 작업은 23:05:21~22에 완료됐고 브라우저 재생 완료를 포함한 턴 종료는 23:05:33이었다. 전체 턴 시간과 첫 응답 지연을 구분해야 한다.
- 23:05:41의 요청은 약 32.6초 뒤 미완성 표정 태그 `[neutral`만 남기고 완료됐다. 정상 답변 실패이며, 기존 로그에는 API 종료 사유가 없어 중단 원인을 확정할 수 없다.
- 앱·음성·기존 기록을 제외하고 같은 Gemini 모델에 짧은 인사를 직접 요청했다. 첫 텍스트까지 14.53초, 전체 14.66초, 종료 사유 `stop`으로 정상 답변을 받았다. 이 검사는 사용자 대화 상태를 변경하지 않았다. 결과는 `tmp/isolated-llm-latency.json`에 있다.
- 따라서 현재 지연에는 외부 LLM 응답 대기가 포함된다. TTS나 누적 대화만을 원인으로 볼 수 없다. API 내부 추론·혼잡·전송 중 어느 원인인지는 이 측정만으로 구분할 수 없고, 확인한 요청 구간에서 요금제 제한 오류는 발견하지 못했다.
