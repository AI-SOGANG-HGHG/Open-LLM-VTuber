# 공통 AI 캐릭터 플랫폼 사전 작업 계획

작성일: 2026년 10월 28일. [팀 목표](../README.team.md)와 [첫 1–2주 계획](plan.md)을 실제 작업 단위로 나눈 제안이다. 역할과 일정은 아직 확정하지 않았으며, 아래 항목은 구현 완료 보고가 아니다.

## 이번 단계의 목표

우선 한 사용자가 서로 다른 캐릭터 두 개를 선택하고, 각 성격에 맞게 대화하며, 기존 대화를 다시 여는 흐름을 확인한다. 그 결과를 바탕으로 캐릭터 설정 화면과 기억 기능의 최소 구현 범위를 정한다.

기능을 고르는 동안 LLM·음성·아바타는 현재 동작한 조합으로 고정한다. 성격 차이와 모델·목소리 차이를 동시에 평가하지 않는다. 다중 사용자 계정 본구현은 이번 준비 단계에 넣지 않는다. Minecraft·방송은 후속 구현 대상으로 포함하고, 관측·행동 인터페이스와 평가 기준은 이번 단계에서 함께 정한다. 두 브라우저 연결의 상태 분리는 로컬 실행의 정확성을 확인하기 위해 점검한다. 10월 29일 확정 사항은 [시스템 방향](system-direction.md)을 따른다.

## 출발점

| 구분 | 현재 근거 |
|---|---|
| 실제 확인 | Windows 한 대에서 서버 기동, Gemini 응답, 한국어 합성 음성 입력의 전사, 음성 데이터 전달을 확인했다. [실행 기록](local-first-run.md) 참고. |
| 로컬 변경 | Edge TTS·WebSocket 수정, 시작·종료 스크립트와 실행 기록은 현재 작업 브랜치의 미커밋 변경이다. 팀 공통 기준으로 공유하는 작업이 남아 있다. |
| 미확인 | 실제 마이크·스피커·화면의 아바타 동작, 대화 중단, 장시간 사용, 두 번째 PC 재현. |
| 프론트 별도 작업 | `origin/feat/frontend-source`의 `967211c`에 편집 가능한 화면 소스와 개발 안내가 있다. 현재 `main`의 빌드된 프론트 서브모듈과 구조가 다르며, 아직 이 작업 폴더에 통합하지 않았다. |

## 우선순위와 완료 기준

| 순서 | 작업 | 해야 할 일 | 완료 기준 | 담당 제안 |
|---|---|---|---|---|
| 1 | 실행 기준 정리 | 로컬 실행 수정만 검토해 공유할 변경으로 묶는다. Python·잠금 파일·FFmpeg·모델·Gemini 설정을 기록한다. 다른 PC에서 새로 받아 재현한다. | 두 명 이상이 같은 기준 버전으로 실행하고 성공·실패 기록을 남김. 개인 키와 대화는 공유하지 않음. | 환경·총괄 |
| 2 | 실제 사용 점검 | 브라우저에서 한국어 텍스트, 마이크 입력, 소리·입 모양, 대화 중 끼어들기, 5턴 연속 대화를 확인한다. 오류 단계와 로그를 기록한다. | [체크리스트](first-run-checklist.md)의 기본 기능 1–6에 결과가 채워지고, 미확인 항목이 명시됨. | 전원, 검증 담당 취합 |
| 3 | 현재 구조와 상태 조사 | 입력 → 대화 → LLM → 음성 → 화면의 연결을 추적한다. 캐릭터 설정, 연결, Agent 메모리, 기록 파일의 소유자·저장 위치·수명을 적는다. | 실제 파일·함수로 연결된 구조도 하나와 상태 표 하나. 공유 가능한 객체와 연결별로 분리할 상태가 구분됨. | 환경·대화·기억 담당 |
| 4 | 프론트 개발 기준 검토 | 기존 `feat/frontend-source` 작업을 먼저 확인한다. 현재 실행 수정과의 충돌, 개발 모드·빌드 후 배포, 기존 타입 오류를 검토한다. | 별도 작업 폴더에서 화면 수정→빌드→백엔드 연결을 재현하고, 통합할 기준·남은 오류·담당자를 정함. | 화면·API, 환경 담당 |
| 5 | 캐릭터·Persona 작은 실험 | 외형·음성·모델은 유지하고 성격만 다른 A/B 설정을 만든다. 서로 다른 `conf_uid`를 쓰고 같은 질문으로 비교한다. | 새 대화·캐릭터 전환 후 말투 차이를 기록하고, 설정 변경이 어느 시점에 반영되는지 설명할 수 있음. | 캐릭터·Persona 담당 |
| 6 | 기록·세션·기억 분리 점검 | 같은 대화, 새로고침, 서버 재시작 후 기록 복원, 새 대화, 다른 캐릭터, 두 브라우저 연결에서 시험용 사실을 확인한다. | 각 상황의 기대 결과·관찰 결과가 표로 정리됨. 다른 연결·캐릭터의 기록이나 문맥이 섞이면 최소 재현과 수정 작업을 등록함. | 기억·대화·세션 담당 |
| 7 | 첫 구현 범위 확정 | 위 결과를 모아 캐릭터 설정 필드, 저장·변경 적용, 대화 기록, 기억 범위와 UI·API 입출력을 정한다. | 작업별 담당자·선행 작업·완료 기준을 갖춘 구현 목록과, 설정 변경→실제 응답까지 확인할 첫 구현 한 개를 합의함. | 전원 |

1–3과 5–6은 실행 가능한 현재 코드를 기준으로 진행할 수 있다. 4의 프론트 검토는 백엔드 조사와 병행할 수 있지만, 화면 구현을 시작하기 전에 개발 기준을 맞춘다. 7은 조사 결과를 보고 결정한다.

## 코드에서 먼저 볼 지점

| 관심사 | 기존 연결점 | 조사할 내용 |
|---|---|---|
| 캐릭터 설정 | `src/open_llm_vtuber/config_manager/character.py`의 `CharacterConfig` | 현재 `conf_uid`, 이름, `persona_prompt`, 모델·음성 설정 중 재사용할 필드 |
| 시스템 지침 구성 | `src/open_llm_vtuber/service_context.py`의 `construct_system_prompt()` | 성격 지침과 표정·도구 지침이 합쳐지는 순서, 설정 변경 후 Agent 갱신 |
| 대화 입출력 | `src/open_llm_vtuber/websocket_handler.py`, `conversations/conversation_handler.py`, `conversations/single_conversation.py` | 텍스트·음성 입력, 응답·음성 전달, 오류·중단 신호 |
| 기록 저장 | `src/open_llm_vtuber/chat_history_manager.py` | `conf_uid`·`history_uid`와 JSON 파일의 관계, 생성·복원·삭제 |
| 현재 대화 문맥 | `agent/agents/basic_memory_agent.py`의 `_memory`, `set_memory_from_history()` | 기록을 읽어 메모리로 옮기는 시점, 새 대화·전환·중단 시 초기화 |
| 연결별 상태 | `websocket_handler.py`의 `_init_service_context()`, `service_context.py`의 `load_cache()` | 어떤 객체가 참조로 공유되고 어떤 상태가 접속별로 나뉘는지 |
| 캐릭터 전환 | `websocket_handler.py`의 `_handle_config_switch()`, `service_context.py`의 `handle_config_switch()` | 현재 설정을 덮어쓰는 범위, 이전 기록과 캐릭터 ID 처리 |

특히 접속별 컨텍스트를 만들면서 기본 `agent_engine` 객체를 넘기고, `load_cache()`에서 같은 객체를 대입하는 코드를 확인했다. Agent는 `_memory`를 수정한다. 이는 상태 공유를 우선 점검해야 한다는 정적 분석 근거이며, 다른 연결의 대화가 실제로 섞였다는 실행 결과는 아직 아니다. 새 대화가 다른 창의 문맥을 초기화하는지도 함께 확인한다.

프론트 소스 브랜치는 `run_server.py`와 `server.py`도 변경한다. 현재 로컬의 WebSocket 수정이 통합 과정에서 사라지지 않게 검토한다. 해당 브랜치 문서에 남은 타입 검사 오류를 성공으로 바꿔 적거나, 해결한 것으로 가정하지 않는다.

## 미리 준비할 공통 자료

| 자료 | 최소 내용 |
|---|---|
| 실행 기록 | 기준 커밋, OS·Python·도구 버전, 모델·음성 설정, 실제 명령, 성공·실패 단계 |
| 구조도·상태 표 | 파일·함수 간 흐름과 설정·세션·Agent 문맥·기록의 소유자·저장 위치·초기화 시점 |
| 캐릭터 설정 초안 | 고유 ID, 표시 이름, 역할·성격, 말투, 언어, 응답 길이. 기존 `persona_prompt`로 표현 가능한지 먼저 확인 |
| 공통 평가 질문 | 자기소개, 과제 시작이 어려운 상황, 초보자용 개념 설명, 시험용 사실 회상. A/B에 같은 순서로 질문 |
| 동작 계약 | 새 대화·캐릭터 변경·설정 저장·재접속·기록 삭제가 무엇을 바꾸고 무엇을 유지하는지 |
| 구현 작업 목록 | 담당 제안, 선행 작업, 변경 후보 파일, 관찰할 결과와 완료 기준 |

캐릭터 예시에는 API 키를 넣지 않는다. 공유할 예시의 위치와 Git 제외 규칙을 확인하고, 개인 `characters/` 설정을 무심코 강제로 추가하지 않는다.

## 첫 1–2주 진행안

| 시점 | 진행할 일 | 회의에서 볼 자료 |
|---|---|---|
| 시작 1–2일 | 로컬 실행 수정 검토, 두 번째 PC 실행, 실제 마이크·화면 확인 | 실행 기록과 실패 목록 |
| 1주차 나머지 | 코드·상태 조사, Persona A/B, 기록·세션 분리 점검, 프론트 소스 검토 | 구조도, 비교 결과, 재현 가능한 문제 목록 |
| 2주차 앞부분 | 캐릭터·대화·기억·세션의 책임과 동작 계약 결정 | 설정 초안, 상태 전이, UI·API 입출력 초안 |
| 2주차 나머지 | 합의한 설정 변경 한 가지를 기존 대화 경로에 연결해 확인 | 변경 전후 응답과 설계 수정 사항, 후속 구현 목록 |

이는 가용 시간에 맞춰 조정할 초안이다. 지금 바로 시작할 순서는 **실행 기준 공유 → 실제 사용 확인 → 상태 분리 조사**로 잡는다.

장기 기억의 첫 범위는 기록 복원 결과를 본 뒤 정한다. 필요하다면 사용자가 명시적으로 알려 준 시험용 사실을 캐릭터별로 저장·조회·정정·삭제하는 작은 실험부터 검토한다. 요약·벡터 검색·새 Agent 프레임워크 도입은 기존 모듈로 해결되지 않는 요구가 확인된 다음 결정한다.
